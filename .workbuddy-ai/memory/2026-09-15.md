# 2026-09-15 — IndoKerja.id Job Application Management

## What this project is

Assessment submission: a simplified Job Application platform ("IndoKerja.id").
React + TS + Vite frontend, NestJS + TS backend, PostgreSQL + Prisma, REST API.
Brief is in Indonesian; all decisions below were confirmed with the user through
a structured grilling session before any code was written.

## Environment setup (IMPORTANT — non-obvious)

The machine had **no PostgreSQL and no Docker**, and `winget install
PostgreSQL.PostgreSQL.16` fails with **HTTP 403 from EnterpriseDB's CloudFront
CDN**. Working solution:

- Downloaded the Zonky embedded-Postgres binaries from Maven Central:
  `https://repo1.maven.org/maven2/io/zonky/test/postgres/embedded-postgres-binaries-windows-amd64/16.2.0/...jar`
- A jar is a zip: unzip -> `postgres-windows-x86_64.txz` -> decompress with
  Python `lzma` (no `xz` binary on this machine) -> real PostgreSQL 16.2 binaries.
- Installed to `C:\Users\bryan\.workbuddy-ai\binaries\pgsql\` (isolated, not
  polluting the user's system).
- Cluster initialized with `initdb -U postgres --auth=scram-sha-256`.
- **The embedded distribution ships only `postgres.exe`, `initdb.exe`, `pg_ctl.exe` —
  NO `psql`.** Database/role creation is therefore done with a Node script using
  the `pg` driver, not `psql`.

**Critical gotcha:** the sandbox reaps all descendant processes when a tool call
returns, regardless of `DETACHED_PROCESS`/`CREATE_NEW_PROCESS_GROUP` flags. A
naive `pg_ctl start` reports success and then the server is dead. Solution:
`~/.workbuddy-ai/binaries/pgsql/keepalive.py` launches postgres AND stays alive in
a foreground loop, run via `run_in_background=true`. It polls the socket, writes
`READY` on success, and shuts down when a `STOP` file appears.

- **Windows path gotcha:** native `.exe`s launched from Git Bash need Windows-style
  paths (`C:/Users/...`). POSIX paths (`/c/Users/...`) fail with "No such file or
  directory". Same for Python invoked from Git Bash.

- Database: role `indokerja` / password `indokerja`, DB `indokerja`, port 5432.
- **`prisma migrate dev` needs `CREATEDB` on the role** (shadow database). Granted
  via `ALTER ROLE indokerja CREATEDB`.
- npm install on the OneDrive path took ~12 minutes for 701 packages.

## Decisions made (all user-confirmed)

Architecture: NestJS (not Express); two-folder monorepo `backend/` + `frontend/`,
no workspace tooling; Tailwind + hand-rolled components (no component library);
Swagger at `/api/docs` **plus** hand-written `docs/API.md`.

Domain model:
- Single `User` table + `Role` enum (`JOB_SEEKER` | `COMPANY`), company-only
  descriptive fields split into a 1:1 `CompanyProfile`. Role immutable.
- `Application` has a denormalized `status` column AND an append-only
  `ApplicationHistory`. Both written in ONE transaction. History is authoritative
  if they ever disagree. Initial `APPLIED` entry written at apply time.
- Duplicate applications blocked by `@@unique([jobId, applicantUserId])` — the DB
  constraint is the guarantee, the service pre-check is just a friendly path.
- **Any status is reachable from any other** — explicitly NO state machine. No
  terminal status; un-rejecting is allowed. `Applied` is system-set only.
- Job has `isActive` boolean (visibility, not lifecycle). No job delete, no
  application withdraw, no bookmarks.
- Salary structured (`salaryMin`/`salaryMax`/`currency`); both null = "Negotiable".

Security:
- Access token 15m **in memory only**; refresh token 7d in `httpOnly` cookie,
  stored server-side as a **bcrypt hash** with rotation on use and real
  server-side revocation on logout.
- `authorization` = resource-ownership checks (derived from DB, never from request
  body) → **404 not 403** for cross-tenant access, to avoid leaking existence.
  `role` = actor-level checks for reads/creation. Two separate guards.
- `helmet`, `@nestjs/throttler` (tighter on login/register), bcrypt cost 10,
  timing-equalized login (dummy hash compare when email absent).

## ADRs written (docs/adr/)

- `0001` single User table with Role discriminator
- `0002` status history authoritative, current status denormalized
- `0003` duplicate applications prevented by unique constraint
- `0004` access token in memory, refresh token httpOnly cookie + revocation
- `0005` authorization guards mutations, role guards reads

`CONTEXT.md` at the repo root is the domain glossary (glossary only, no
implementation details). It explicitly lists rejected terms — notably that
"Candidate" is role-relative, not an entity, and that "Withdrawn" and "Closed"
are deliberately not statuses.

## Bugs found and fixed (worth remembering)

1. **`RefreshTokenDto.refreshToken` was not `@IsOptional()`** — with the global
   `ValidationPipe({ whitelist: true })`, a browser sending the refresh token
   *only* as an httpOnly cookie (empty body) got a **400 before the cookie was
   ever read**, breaking refresh and logout entirely. This is the exact failure
   the 90-assertion suite caught. Any DTO field that is sourced from a cookie
   rather than the body must be optional.

2. **`ThrottlerGuard` cannot be constructed manually in `main.ts`.**
   `app.useGlobalGuards(new ThrottlerGuard({throttlers:[...]}, reflector, storage))`
   fails with *"Nest could not find ThrottlerStorage element"* because
   `ThrottlerStorage` only exists once `ThrottlerModule` is imported. Correct
   approach: `ThrottlerModule.forRoot([{name:'default', ttl, limit}])` in
   `AppModule` + `{ provide: APP_GUARD, useClass: ThrottlerGuard }`.

3. **`nest build` emitted `dist/src/main.js` instead of `dist/main.js`.**
   Cause: `prisma/seed.ts` was inside the compile scope, so `rootDir` widened to
   the project root. Fix: a `tsconfig.build.json` with `rootDir: "./src"` and
   `prisma` excluded from `include`.

4. **TypeScript incremental cache masked source changes.** After editing source,
   `npx nest build` produced no output file changes, so stale JS kept running
   (the `ThrottlerStorage` error persisted across two "successful" builds).
   Also the sandbox's bulk-delete guard blocks `rm -rf dist` (reports
   `SAFE_DELETE_BULK_CONFIRM_REQUIRED`), so `deleteOutDir` silently fails.
   Reliable rebuild: `rm -f tsconfig.tsbuildinfo && npx tsc -p tsconfig.build.json --incremental false`.

5. **`$transaction([...])` array form only accepts `PrismaPromise`s.** Passing an
   `async` helper's `Promise` fails to type-check. Use `Promise.all` for
   independent reads, `$transaction` for writes that must be atomic.

6. **`@IsOptional()` silently disables every other validator on the field.**
   `companyName` had `@ValidateIf(role === COMPANY)` + `@IsNotEmpty` +
   `@IsOptional()`. Because `@IsOptional()` short-circuits for `undefined`, a
   COMPANY could register with **no company name at all** — the exact case the
   `@ValidateIf` was meant to forbid. Caught by the Jest suite. Fix: drop
   `@IsOptional()`, keep `@ValidateIf` alone. **Rule: never combine
   `@IsOptional()` with conditional-required validation.**

7. **`@IsNotEmpty()` accepts whitespace-only strings.** It only checks
   `value !== ''`, so `"   "` passed and the service then `.trim()`ed it to `""`
   — storing a job with an empty title. Caught by the Jest suite. Fix: a reusable
   `@IsNonBlank()` decorator in `src/common/validators/is-non-blank.validator.ts`
   that validates the *trimmed* value. Now applied to every required text field.
   **Rule: validate what will be persisted, not what was sent.**

8. **Duplicate email returned 401 instead of 409** (`UnauthorizedException` in
   `auth.service.ts`). Mislabelled — the credentials are irrelevant, the email is
   simply taken, and a 401 would push the client to re-authenticate pointlessly.
   Fixed to `ConflictException`.

## Testing notes (non-obvious)

- The e2e suite shares **one IP**, so the production rate limits (5 registrations
  per minute) trip it almost immediately: 86 of 102 tests failed with 429 on the
  first run. Fix: `THROTTLE_LIMIT*` env vars read in `app.module.ts` and
  `auth.controller.ts`, lifted in `test/setup-e2e.ts`. The limits themselves are
  asserted on the decorator metadata instead of by counting requests.
- `@Throttle` metadata **overrides** the module default (`routeOrClassLimit ||
  namedThrottler.limit` in `throttler.guard.js`), so an env var in
  `ThrottlerModule.forRoot` alone does **not** affect decorated routes.
- Jest e2e needs `setupFilesAfterEach`-style env loading (`test/setup-e2e.ts`)
  for `JWT_ACCESS_SECRET`, otherwise `AppConfigService` throws at bootstrap.
- supertest types `set-cookie` as `string` but it is an array at runtime — use a
  narrowing helper rather than casting at each call site.

## Code review (committed as `c6fda49`)

Two-axis review as the `implement` skill requires — standards (CONTEXT.md, the 5
ADRs, docs/API.md) and spec (the assessment brief). **Every agent finding was
verified before acting; two were partly or wholly wrong.**

Confirmed and fixed:
- **`docs/API.md` documented a phantom `historyEntry` field** on the status-change
  response. No code path produces it. The real shape is
  `{id, status, previousStatus, changed}`; History is a separate re-fetch.
- **ADR-0004 was stale and understated the system.** It claimed we do *not*
  implement reuse detection, but `RefreshTokenService.consume` *does* call
  `revokeAllForUser`. Rewritten, plus a new "Revocation scope" section: the scope
  is every session for that user, not a per-device "token family", because tokens
  are salted bcrypt hashes (not searchable) so there is no family to walk. The
  real cost — a stray second-tab retry logs the user out everywhere — is why the
  frontend collapses concurrent refreshes into one promise.
- **CONTEXT.md rejects "Applicant" for the Company's view (use "Candidate")** yet
  the DTO field, page name, route and visible labels all said "Applicant". Renamed
  `CandidateResponseDto.applicant` → `candidate`, `ApplicantsPage` →
  `CandidatesPage` (via `git mv`) and its route, and the Swagger tag. The Prisma
  *relation* stays `applicant` — CONTEXT.md tolerates storage-level naming.
- **Duplicated company-name fallback** (`companyProfile?.companyName ?? email`) in
  4 places = Shotgun Surgery risk. Extracted `APPLICATION_JOB_SELECT` +
  `toApplicationJob()` in `applications.service.ts`. `jobs.service.ts` was already
  clean (`JOB_INCLUDE` + `toResponse`), so no change needed there.

Rejected after verification (agent was wrong):
- A claimed off-by-one in `apitest.js` ("91 checks"): `grep -c "^  *check("` gives
  exactly 90 and the script reports 90. The agent had counted the function
  definition.

Deliberately left alone:
- "applicant count" in a UI string — a plain-English count, not the disputed
  entity term.
- `application.applicant` (the Prisma relation name) — storage-level, tolerated.
- The `APPLIED` status returns 400 from `PATCH /status` by design (system-assigned,
  append-only). This is defensible but does not honour the brief literally, so it
  is documented in `docs/API.md` and the README rather than "fixed".

**Lesson: the reviews' most valuable output was the stale ADR, not the code
smells.** A documented decision that no longer matches the code is worse than no
documentation, because it actively misleads a reader who trusts it.
